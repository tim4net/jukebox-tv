### Required fix #2 (double-launch race) — TDD
- [test-first] Added
  `aPendingInstallIsLaunchedExactlyOnceWhenThePressRacesTheForegroundHook`:
  download completes backgrounded (pending set), then the foreground hook
  schedules its launch while the user presses OK — the press claims and
  launches, then the hook's scheduled launch runs. Run: FAILED for the
  expected reason — `assertEquals(1, launcher.calls)` at the "exactly once"
  assert saw 2 launches (press + hook both launched the same pending file:
  installAsync read mPendingInstallPath unsynchronized, onAppForeground
  captured it too, both called launchOrDefer → both launched).
- [impl, smallest change] launchOrDefer now claims the pending launch
  atomically: signature `launchOrDefer(path, freshDownload)` — fresh downloads
  (this caller just downloaded it, nothing pending can race) always launch;
  pending paths are claimed under mDownloadLock via `claimPendingLaunch(path)`
  (compare-and-clear, true exactly once per pending file). The losing caller
  logs "launch skipped: <path> already launched by another caller (install
  press vs foreground hook)" and does NOT launch. Pending set/clear moved into
  `setPendingInstall` (synchronized) for visibility. installAsync now captures
  the pending path locally (no unsynchronized re-read) and passes fresh=false;
  the fresh branch passes fresh=true; onAppForeground passes fresh=false.
  Decision logic stays one place (launchOrDefer); I/O at the edges unchanged.
- Run: JukeboxUpdateInstallTest 12/12 PASS (new race test green: launcher
  called exactly once, loser logged "already launched").
