## Step 2: root cause from code and logs
- Repro (Nina 2477/2478, .nina/roux2477.txt bug (2)): after the 2477→2478 update install the app cold-started into the room and the player opened the CURRENT room song from 0 (first heartbeat pos=4027ms at 12:03:52) while the room was ~2 minutes in — the phone listeners and the TV were ~2 min apart.
- Code path (all read): cold start → JukeboxRoom.start() → setupRoom (GET /api/r/{room}/state, body discarded except isClosedState) → ws connect → server "play" + "state" → JukeboxRoom.onPlay → `PlaybackPresenter.instance(mAppContext).openVideo(videoId)` = openVideo(videoId, false, -1, false): pendingPosMs = -1, so VideoStateController never seeks → song starts at 0. The 2470 foreground-return fix (JukeboxRoomController.pendingPosMs → mLastPosMs) only uses LOCAL memory (last locally observed/reported position) which a cold-started process does not have → -1 → "opening exact room videoId ... (attempt 1, posMs=-1)" (JukeboxRoomController ~375), i.e. same start-at-0 on the resume/reopen paths too.
- What the room protocol provides (verified against the deployed server, read-only, no server change): every "state" broadcast carries `now` (server epoch ms) and nowPlaying {songId, videoId, title, startedAt (epoch ms), paused, pausedAt, durationMs}. The phone/TV web apps compute the room position exactly as expectedPositionSec(): `end = paused && pausedAt != null ? pausedAt : serverNow; sec = (end - startedAt)/1000`, capped at durationMs, min 0 (phone JS /tmp/opencode/room.html:730-738, tv JS:453-461). The Android client parses none of these fields today (JukeboxProtocol.parse reads nowPlaying songId/videoId/title only) — so on cold start the TV cannot seek and starts the room song at 0.

## Step 3: production change (smallest, per spec)
Files: common/src/stjukebox/java/net/tfour/jukebox/room/{JukeboxProtocol,JukeboxRoomClient,JukeboxRoom,JukeboxRoomController}.java only.1. JukeboxProtocol.java (pure decoder): parse what the protocol actually carries — `now` (server clock, top-level Number) and nowPlaying `startedAt`/`paused`/`pausedAt`/`durationMs` — into Message via a new `millis()` helper (null when absent/non-numeric). New getters: getServerNowMs(), getNowPlayingStartedAtMs(), isNowPlayingPaused(), getNowPlayingPausedAtMs(), getNowPlayingDurationMs(). Protocol javadoc updated to the real state shape. No encoding change; bridge/server untouched.
2. JukeboxRoomClient.java: volatile snapshot-position record (mPosVideoId/mPosPaused/mPosStartedAtMs/mPosPausedAtMs/mPosDurationMs/mPosServerNowMs/mPosReceivedAtMs — lock-free main-thread reads like mSongFromState) recorded by captureRoomPositionLocked() from every "state" message; cleared on idle (nowPlaying null), on song-clear (clearSongLocked: stop/closed/song-clear) and on snapshots without position data. New lock-free estimate roomPositionMs(videoId): `(paused && pausedAt>0 ? pausedAt : serverNow) - startedAt`, serverNow = snapshot `now` + local elapsed since receipt ("position + server time elapsed"; local-clock fallback when the snapshot carries no `now`), capped at durationMs, >= 0, video-scoped (stale position of another song never applies), -1 when unknown. Exactly the phone/TV web-app formula (expectedPositionSec).
3. JukeboxRoom.java: getRoomPositionMs(videoId) (guards inactive/null client → -1). onPlay foreground branch: posMs = getRoomPositionMs(videoId); >= 0 → openVideo(videoId, false, posMs, false) + log "opening at the room position <posMs>ms (snapshot startedAt + server time elapsed)", else the byte-identical old openVideo(videoId). Backgrounded branch unchanged.
4. JukeboxRoomController.java: pendingPosMs() — local last-observed position (2470) still wins; on a cold start (no local memory) it now falls back to JukeboxRoom.getRoomPositionMs(roomVideoId), so the resume/reopen paths ("opening exact room videoId", posMs was -1 on 2478) also seek to the room estimate. -1 keeps the old behavior when unknown.
No server/bridge change, no jukebox-bridge/vj.service touch, no versionCode change, no secrets, no test weakened.
