## 1. Double-open on resume (BLOCKING 1)

Root cause: `JukeboxRoomController` treated a young in-flight marker as stale whenever no player was attached yet. `onNewVideo` sets that marker from inside `openVideo`, before the player activity exists. `JukeboxRoom.onPlay` opens the video before it notifies listeners so the resume check already sees the load. Calling the marker stale in that window opened the same video a second time.

Fix, in `JukeboxRoomController`:
- `LOAD_IN_FLIGHT_TIMEOUT_MS` stays 15_000 (the 8s change is reverted). Age uses `SystemClock.elapsedRealtime`.
- A marker younger than 15s defers, including when no player is attached. Only age past 15s is stale.
- Removed `isLoadHolderAlive()` ("no player" is not staleness).
- `clearLoadThatNeverStarted()` drops the marker only when `openVideo` did not start a player. `JukeboxRoom.onPlay` calls it if the app backgrounded between the foreground check and the launch. The existing `openRoomVideo` backgrounded-launch finally-block still clears the marker too.

The marker is still set in `onNewVideo`. Delaying it until a player attaches would make the listener resume miss the in-flight load and open twice (the warning in `JukeboxRoom` around the play path).

## 2. Cold launch before the song is known (Nina 2481)

`JukeboxJoinActivity` ran one resume tick, saw no current song, and stopped. The later websocket state never retried, and focus stayed on Browse.

`onStateChanged` now treats the idle-to-playing edge as the moment the song is known: it calls `resumeRoomSongIfNeeded("join:onState")` synchronously. A non-null `via` already opens a snapshot-sourced song (resume-after-return). A fresh foreground snapshot with `via == null` and no pending return still waits for that song's own play.

If that synchronous open returns false, no extra retry is posted. If it cannot finish (no controller, or the check says to keep asking), `startResumeRetry("onState")` runs.

## 3. Default focus only on idle-to-playing (SHOULD FIX 3)

`mRoomSongActive` records the last applied playing state. The QR is requested only when that flag flips to playing. A later state or `onResume` does not pull focus back off Browse.

Playing-to-idle hands focus to Browse. `setFocusable(false)` clears focus first, so the QR's `hasFocus()` is captured before that call and Browse is requested from that answer.

## 4. Join-screen test order (BLOCKING 2)

`JukeboxJoinActivityForwardTest.resetProcessState` (before and after) stops the room, idles the main looper while that instance is still the singleton, quits its handler thread, nulls the singleton, and repeats the drop so a late callback cannot recreate it. It also clears `JukeboxForeground.setTestOverride(null)`. `resetForTests()` does not clear the override. The new room-handler callbacks are not the test's own `Handler`.

## 5. Tests observe public events (SHOULD FIX 5)

`JukeboxJoinFocusTest` moved to `net.tfour.jukebox.room` so it can build the package-private `JukeboxRoom` the same way the cold-launch test does. It drives focus and OK-on-QR through room messages and view events. No log-text asserts, no reads of room fields.

`JukeboxResumeAfterReleaseTest` no longer plants controller fields or asserts log lines. Opens are the activities `openVideo` starts. Stale loaded state is a late `onVideoLoaded` after engine release. A stale in-flight load is `onNewVideo` plus a 60s `elapsedRealtime` advance. The reopen cap is exhausted with mismatched `onVideoLoaded` calls, then the engine release must still open the room song once. The 9s/16s pending-load cases stay public (`onNewVideo` + `ShadowSystemClock`).

Singleton resets still use the private `sInstance` fields. There is no public reset. That is fixture teardown, same as the cold-launch test.

`JukeboxJoinColdLaunchTest` and `JukeboxJoinFocusTest` set `@Config(qualifiers = "w960dp-h540dp-land-television-xhdpi")`, the same TV size `JukeboxJoinScreenRenderTest` uses and the same 1920x1080 `layoutLikeTheTv()` already applied. Without it, the next traversal laid the window out at 320x470, the Browse column measured 0px wide, and `requestFocus()` returned false. Assertions are unchanged.

`JukeboxExactlyOnceOpenTest` and `JukeboxJoinColdLaunchTest` assertions were not weakened.
