## Item 6 — partyq / bridge (read-only)

The Android client does not get position fields from the bridge process. It is its
own room WebSocket client and receives the server `state` broadcast.

The server does send them:

- `.partyq-ro/src/room.ts:1589-1603` — `broadcast()` sets `const now = Date.now()`
  and sends `{ t: "state", room, nowPlaying: np, queue, listeners, now, ... }`
  on every socket, including the TV.
- `.partyq-ro/src/room.ts:1723-1727` — `nowPlayingView()` always sets
  `startedAt` (`metaNum("startedAt") ?? Date.now()`), `paused`, and
  `pausedAt` (the meta number while paused, otherwise `null`), plus `durationMs`.

The bridge does not re-send them:

- `.partyq-ro/bridge/bridge.mjs:425-432` — `handleRoomMessage` on `t:"state"`
  only calls `onNowPlaying(msg.nowPlaying)`.
- `.partyq-ro/bridge/bridge.mjs:408-422` — `onNowPlaying` reads `videoId`,
  `songId`, and `title`, then starts the VJ. It drops `now`, `startedAt`,
  `paused`, `pausedAt`, `durationMs`.
- `.partyq-ro/bridge/bridge.mjs:492` emits `{ t: "next" }`, `:514` emits
  `{ t: "ping" }`, `:563` emits `{ t: "bridge-hello" }`. No `state`.

So a real room `state` on the TV socket does carry `now` and `startedAt`, and
`pausedAt` when the song is paused. Missing `now` is not what the current server
sends; the -1 rule is still required for a snapshot that omits it.

Web listen-along (`/.partyq-ro/src/sync.ts`) for phase 2:

- `:36` `DRIFT_TOLERANCE_SEC = 2` — the 2000 ms margin these tests pin.
- `:38-49` `expectedPositionSec` uses `(paused && pausedAt != null ? pausedAt : serverNow) - startedAt`,
  caps at `durationMs`, and clamps at 0. It does not return "unknown" near the end.
  The Android review wants -1 instead of seeking to the end. These tests follow the review.
- `:62-66` `syncAction` returns `pause` when `np.paused` and the player is not paused.
  That is the open-paused behavior in item 5.
